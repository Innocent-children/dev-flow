# Dev Flow 下一阶段功能规划

# 一、目标

Dev Flow 下一阶段不再继续增加更多流程节点，而是集中解决四个用户能直接感受到的问题：

1. Agent 一直重复时，能够停下来；
2. Agent 想改任务范围外的文件时，先询问用户；
3. 任务没有真正完成时，不能进入 `DONE`；
4. 会话中断后，能够从剩余工作继续，而不是重新摸索。

原则是：**已有能力继续改好，缺失能力补齐，不重复建设。**

---

# 二、当前情况

| 功能             | 当前情况                                                     | 结论                                     |
| ---------------- | ------------------------------------------------------------ | ---------------------------------------- |
| 自动刹车         | TASKS 按分析结果建立验证计划；TEST 可用具体原因增加预算；第三次精确重复后暂停 Task | 当前约定已补齐，等待真实使用验证         |
| 范围外文件先询问 | 当前源码已增加结构化写入前询问、决定持久化和最终路径检查     | 第一版已补齐，等待真实使用验证           |
| 完成前检查       | 已有独立的 Delivery 阶段，测试、理解确认、未完成检查等不满足时不能进入 `DONE` | 已经实现，但仍有检查漏洞，展示也不够直观 |
| 任务接续         | 当前 Task 保存在本地，同一 Host 可以根据仓库重新打开正在进行的 Task | 已经实现，后续重点改善恢复后的使用体验   |

# 三、自动刹车

> 实施状态：第一版已在当前源码中完成，尚未扩大公开稳定支持范围。

## 当前源码已经有的能力

Dev Flow 当前在 TASKS 完成需求、设计、工作拆分、影响面和现有测试结构分析后，保存：

* 计划执行的检查和每项具体理由；
* 预计自动命令数量；
* 是否预计完整测试套件；
* 是否预计新增或修改测试代码。

Task 创建时不再冻结最终预算。Evidence 按当前 Task Plan revision 统计；计划正式重建后使用新预算，
旧记录仍保留。容量不足时，Host 在额外命令执行前用 `new_impact`、`new_risk`、
`verification_failure` 或 `verification_gap` 中的具体依据增加当前需要的部分，Core 保存原因、增加量和
调整前后预算并留在 TEST。无具体原因、无新增检查或没有实际增加会被拒绝。

预算允许完整套件不代表本次有必要运行。Host 每次都要重新判断广泛影响、定向检查是否足够、待补的
具体风险和仓库检查点要求；完整套件 Evidence 保存本次 `full_suite_reason`。

当前源码还会保存最近三次测试尝试，并在以下任一情况第三次精确重复后进入 `BLOCKED`：

* 同一自动检查与失败相同；
* 完整测试结果相同；
* 测试返回实现阶段，且连续修改路径和失败内容相同。

## 当前边界

Core 能确认结构化计划、预算变化和结果，不能解析任意 shell 或判断自然语言理由是否真的充分。
Codex/DeepSeek Skill 负责命令和测试文件修改前的相关性判断；Core 仍会对提交结果和 Git surface 做
最终校验。当前不会判断重复读文件、普通输出或经过时间。

## 第一版实现

在现有验证次数限制上增加“重复识别”：

### 第一版只识别三种情况

1. 同一个检查连续失败 3 次；
2. 同一个检查连续运行 3 次，结果没有变化；
3. `TEST → IMPLEMENT → TEST` 连续循环 3 次，并且修改文件和失败内容基本相同。

触发后暂停任务：

```text
任务已暂停

原因：
同一个认证测试连续失败 3 次，
最近两次修改没有改变失败结果。

请选择：
- 换一种实现方式
- 回到设计
- 再允许一次尝试
- 停止任务
```

## 实现方式

不需要新增一套流程。

可以复用现有的：

* Task 历史记录；
* 测试名称和结果摘要；
* 修改路径；
* `BLOCKED` 节点；
* blocker 解除后返回原阶段的能力。

第一版不判断所有 Agent 行为，只处理规范化后能够精确确认的测试循环。不同失败继续流转；用户明确
允许后解除 blocker 并获得一次继续机会，下一次仍然完全重复时再次暂停。等真实使用稳定后，再考虑
重复读文件、重复输出和运行时间限制。

## 验收方式

* 同一失败出现 3 次后，不能自动执行第 4 次；
* Task 进入暂停状态；
* 用户可以允许一次重试；
* 解除暂停后回到原来的 `TEST` 或 `IMPLEMENT`；
* 不同失败不能被误判成同一个循环。

# 四、范围外文件先询问

> 实施状态：第一版已在当前源码中完成，尚未扩大公开稳定支持范围。

## 当前已经有的能力

当前项目已经保存：

* 初始范围；
* 明确不做的内容；
* Requirements 中的范围；
* 每个工作项预计修改的路径；
* Implementation 实际修改的路径；
* Action 开始前后真实发生变化的文件。

Task Plan 中已经有 `ExpectedPaths`，Implementation 中也已经有 `ChangedPaths`。

当前 Core 还会检查 Agent 上报的修改路径是否真的出现在仓库变化中，避免 Agent 随便填写文件列表。

当前源码进一步保存文件范围请求、用户选择、原因、适用的 Task Plan revision、一次授权状态和本 Task
累计修改路径。

## 第一版实现

第一版直接比较：

* 当前 Task Plan 全部 WorkItem 的 `ExpectedPaths` 合集；
* Host 准备执行的结构化写入目标；
* Core 从 Action 前后 Git 状态确认的累计 `ChangedPaths`；
* 已使用的 `allow_once` 记录。

多仓库路径使用 repository key。B、C 等附加仓库已经在 Task Repository Scope、Host 已有写权限且
文件属于 ExpectedPaths 时，不因为当前目录位于 A 而询问。

## 第一版行为

### 修改之前

Codex 或 DeepSeek 准备写入文件时，Adapter 先检查：

```text
当前文件
src/config/security.yml

当前 Task Plan 允许修改
src/auth/**
tests/auth/**
```

不在范围内时停止写入：

```text
这个文件不在本次任务范围内：

src/config/security.yml

需要修改的原因：
登录失败次数由这个配置控制。

请选择：
- 只允许修改这一个文件
- 加入本次任务范围
- 不允许修改
```

### 三个选择的含义

**只允许一次**

只为当前修改放行，不扩大整个工作项。

**加入本次任务范围**

返回 `TASKS` 更新 ExpectedPaths；如果需求本身也变化，再使用既有流转返回 Requirements。

**不允许修改**

保持当前范围，Agent 必须换一种方案，或者报告任务无法继续。

### 完成之前

再进行一次最终核对：

```text
本次任务修改了 4 个文件

范围内
✓ src/auth/limiter.go
✓ tests/auth/limiter.test.go

已单独允许
✓ src/config/security.yml

没有说明
! README.md
```

存在“没有说明”的文件时，不允许结束任务。

## 需要注意

Dev Flow 不是文件系统沙箱，Core 也不会拦截 Host 的每一次文件写入。第一版 Codex 覆盖
`apply_patch`，DeepSeek 覆盖 `write`、`edit` 和变更型 `str_replace_editor`。Bash、外部进程和部分
专用工具可能先写入，再由 Core 最终检查发现。

因此，这项功能需要两层配合：

1. Host Adapter 在写入前检查；
2. Core 在提交实现和完成任务时再次检查。

第一层减少乱改，第二层防止漏网文件被带进 `DONE`。

## 验收方式

* 修改预计路径内文件时，不增加询问；
* 修改 Task Scope 内其他仓库的预计路径时，不因当前工作目录不同而询问；
* 修改预计路径外文件时，写入前暂停；
* 用户拒绝后，该文件不能由 Dev Flow 流程继续修改；
* 用户允许后，选择和原因被保存；
* 完成前不能存在没有说明的范围外文件。

# 五、完成前检查

## 当前已经有的能力

这项功能已经比较完整。

当前进入 `DONE` 前必须经过 Delivery，并要求：

* Requirements、Design、Tasks 都是当前版本；
* 当前实现已经通过测试；
* 测试之后没有发生新的仓库变化；
* 已经完成开发者理解确认；
* 没有未验证事项；
* 没有未处理的人工交接事项；
* 所有验收条件都被标记为完成；
* 当前测试记录和理解确认仍然对应当前代码。

如果代码在测试后继续修改，旧的测试和理解确认不会继续用于完成任务。

## 当前不足

### 1. 不要求所有工作项都明确完成

当前 `CompletedWorkItemIDs` 只检查 ID 是否属于当前任务计划，没有要求它必须覆盖全部工作项。

理论上可能出现：

```text
任务计划有 5 项
Agent 上报完成了 4 项
但仍然进入测试和交付
```

### 2. 验收条件被自动标记为满足

进入 `delivery_complete` 时，Core 会根据 Requirements 自动生成一份全部为 `satisfied` 的验收结果，而不是逐项确认每个条件由哪项实现和哪次检查完成。

当前检查比普通 Agent 直接说“完成”严格很多，但还不能真正说明：

> 每一个要求分别是怎么完成的。

### 3. 用户看不到简单结果

现在完成条件分散在 Task、Test、Comprehension 和 Delivery 中。

用户更需要：

```text
还不能结束

✗ 工作项 4 尚未完成
✗ 最后一次修改后没有重新测试
✗ README.md 超出范围且没有说明
```

而不是理解内部节点和字段。

## 改进方向

### 第一项：要求全部工作项完成

进入 `implementation_ready_for_test` 前检查：

```text
CompletedWorkItemIDs
```

必须覆盖当前 Task Plan 的全部必做工作项。

以后如果需要可选任务，再给 WorkItem 增加 `required`，不要默认允许遗漏。

### 第二项：验收条件逐项对应

每个验收条件至少要对应：

* 一个已经完成的工作项；
* 一项当前仍有效的检查，或者一项明确的人工确认。

例如：

```text
连续失败 5 次后锁定
✓ 工作项：实现失败次数限制
✓ 检查：auth-lockout-test

登录成功后计数归零
✗ 没有对应检查
```

第二项不能通过时，任务不能结束。

### 第三项：增加简单的完成结果

CLI、Codex、DeepSeek 和 WebUI 使用同一份结果：

```text
完成前检查

工作项        4 / 4
验收要求      3 / 3
最后修改后测试  已完成
范围外文件      无
未处理失败      无

可以结束
```

或者：

```text
还不能结束

- 还有 1 个工作项没有完成
- 有 1 项要求没有对应检查
```

## 验收方式

* 任一必做工作项未完成时，不能进入测试或 `DONE`；
* 任一验收条件没有对应完成项和检查时，不能进入 `DONE`；
* 最后一次代码修改发生在测试之后时，不能进入 `DONE`；
* 用户能够在一屏内看懂为什么能结束或为什么不能结束。

# 六、任务接续

## 当前已经有的能力

这项能力已经是 Dev Flow 当前最成熟的部分之一。

现在：

* Task 持久保存在本地；
* 新会话可以根据当前仓库找到正在进行的 Task；
* 相同 Host 可以恢复当前节点、revision 和当前 Action；
* 不确定 Action 有单独的恢复处理；
* 用户不需要重新提交一份猜测出来的任务状态。

`OpenTask` 在没有 `new_task` 时会直接查找当前仓库的活动 Task；如果新请求与已有 Task 完全一致，也会返回原 Task。

## 当前限制

### 1. 只支持原 Host 接续

Codex 创建的 Task 不能直接由 DeepSeek 接管，反过来也一样。当前会返回 `HOST_OWNERSHIP_CONFLICT`。

这符合现有安全边界，不需要近期立刻改。

### 2. 恢复后信息仍然偏技术

恢复后用户看到的是：

* 当前节点；
* revision；
* Action；
* blocker；
* Recovery。

用户真正需要的是：

```text
已经完成什么
还剩什么
为什么停在这里
下一步是什么
```

### 3. 没有专门记录“已经试过但失败的办法”

当前有流程历史、流转原因和旧版本记录，但没有一份简单的：

```text
已经试过
- 修改全局重试：失败，影响范围太大
- 修改数据库结构：用户拒绝
```

新会话恢复后，仍可能再次提出之前已经排除的方案。

## 改进方向

### 第一项：增加恢复摘要

每次恢复只展示：

```text
任务：修复登录失败次数限制

已经完成
✓ 需求已确认
✓ 实现已完成

还剩
- 运行一项针对性检查
- 确认实现是否容易维护

上次停止原因
Codex 会话结束

下一步
运行 auth-lockout-test
```

### 第二项：记录失败过的办法

增加一份数量有限的尝试记录：

```text
方案
结果
原因
是否允许再次尝试
```

只记录真正影响后续工作的结果，不记录每一次文件读取和普通命令。

### 第三项：处理中途新增要求

活动 Task 存在时，用户又提出新需求，应让用户选择：

```text
这是：
- 修改当前任务
- 当前任务完成后的下一件事
- 取消当前任务并开始新任务
```

不要由 Agent自行把新要求混入当前任务。

### 第四项：跨 Host 交接放到后面

Codex 与 DeepSeek 互相接管可以作为后续能力，但不应在前面三项完成前开发。

跨 Host 交接时只传递：

* 当前任务；
* 已完成工作；
* 剩余工作；
* 已失败方案；
* 当前限制。

不复制整段聊天记录。

## 验收方式

* 新会话能够找到同一个 Task；
* 恢复后第一屏直接显示已完成、剩余和下一步；
* 已经被用户拒绝的方案不会被再次自动采用；
* 新增要求不会悄悄改变当前任务；
* 同 Host 接续保持稳定后，再考虑跨 Host。

---

# 七、近期不做

以上四项完成前，暂时不增加：

* 新 Agent Adapter；
* 自定义流程图；
* 更多流程节点；
* 远程 WebUI；
* 团队账号和权限；
* 多 Agent 调度；
* OpenSpec / Spec Kit 深度编排；
* 自动 commit、merge 或 push。

下一阶段的重点不是让 Dev Flow“功能更多”，而是让现有功能真正做到：

> **重复时停下，乱改前询问，没完成不能结束，换个会话还能继续。**
