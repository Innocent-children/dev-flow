# Dev Flow 文档国际化策略

[中文](I18N.md) | [English](I18N_en.md)

## 适用范围

本策略管理仓库中的人类可读文档，不定义产品运行时 locale。产品行为权威仍是源码、机器可读
Schema、制品清单和可执行测试；翻译文件只负责以不同语言准确呈现同一组事实。

## 维护语言

根 README 维护以下 9 个 locale：

| Locale | 语言 | 文件 | 角色 |
| --- | --- | --- | --- |
| `zh-CN` | 简体中文 | `README.md` | 仓库默认入口与中文版本 |
| `en` | English | `README_en.md` | 英文版本；其他非中文翻译的 source text |
| `zh-TW` | 繁體中文 | `README_zh-TW.md` | 完整维护 |
| `ja` | 日本語 | `README_ja.md` | 完整维护 |
| `ko` | 한국어 | `README_ko.md` | 完整维护 |
| `es` | Español | `README_es.md` | 完整维护 |
| `fr` | Français | `README_fr.md` | 完整维护 |
| `de` | Deutsch | `README_de.md` | 完整维护 |
| `pt-BR` | Português do Brasil | `README_pt-BR.md` | 完整维护 |

新增 locale 必须同时提供完整初始翻译、语言导航入口和后续维护责任。不得先添加空文件、占位链接
或只翻译标题。

## 选择原则

当前集合在覆盖范围与长期同步成本之间取固定边界：

- `zh-CN` 与 `en` 是产品和技术文档的主要权威语言；
- `zh-TW`、`ja`、`ko` 覆盖主要东亚开发者社区；
- `es`、`fr`、`de`、`pt-BR` 覆盖常见的大型开源开发者 locale；
- 根 README 提供较宽的入口本地化，精确技术参考仍集中维护简体中文与英文版本；
- 不添加没有明确维护责任的 locale，避免版本、安装命令和支持声明长期漂移。

该集合不是完整的运行时语言清单，也不表示其他语言不受欢迎。新增语言必须先满足完整翻译和持续
同步条件。

## 文档覆盖矩阵

| 文档族 | 维护范围 |
| --- | --- |
| 根 `README*` | 上述全部 9 个 locale，结构和产品事实必须一致 |
| `docs/PRODUCT*`、`docs/ARCHITECTURE*`、`docs/ROADMAP*`、`docs/SUPPORT-MATRIX*`、`docs/COMMANDS*`、`MANIFEST*` | 简体中文与英文 |
| Codex / DeepSeek 用户与安装文档 | 当前维护的简体中文与英文配对文件 |
| `CONTRIBUTING*` 与 I18n 策略 | 简体中文与英文 |
| release 和 maintainer 合同 | 按各自维护语言更新；除非已有明确配对，不自动复制为 9 语种 |

覆盖范围是显式合同，不根据目录名称自动推断。某个文档族一旦列出多个 locale，任何事实性修改都
必须同步该文档族的全部维护文件。

## 同步合同

任何改变用户可见行为的改动必须在同一 Pull Request 中：

1. 更新全部 9 个根 README；
2. 更新 `docs/PRODUCT.md` 与 `docs/PRODUCT_en.md`；
3. 按影响面更新 Architecture、Support Matrix、Command Reference、Roadmap、Host package README、安装或调用文档；
4. 在 Pull Request 验证说明中列出所有文档路径。

版本发布改变公开版本、bundled Core、平台、Host 兼容范围、安装命令或 release evidence 时，也
必须在发布前同步所有根 README 以及受影响的支持、命令与 package 文档。

纯文档修正必须修改所有包含同一错误陈述的维护 locale。翻译尚未同步时，不得把产品改动、
文档变更或 release 状态报告为可合并、Complete 或 ready to publish。

## 安装命令与版本身份

面向普通用户的公开安装示例使用 npm `latest` dist-tag：

```text
dev-flow-codex@latest
dev-flow-deepseek@latest
```

精确版本号仍用于 Support Matrix、Release Tag、npm 版本链接、bundled Core identity、制品 digest
和最终 Journey 证据。不得为了统一文本把这些证据身份替换为 `latest`，也不得在普通安装示例中
长期固定一个已经发布的旧版本。

安装与命令文档必须对照可执行实现核对：

- npm package 名称、`bin` 与平台约束来自对应 `package.json`；
- Codex CLI 子命令和参数来自 `packages/codex/bin/dev-flow-codex.mjs` 的实际 parser；
- DeepSeek 安装与移除形态来自 DSH lifecycle tests 和 final-artifact Journey；
- packaged Core 命令来自 `cmd/dev-flow/main.go`；
- MCP tool 名称、读写属性与用途来自 `internal/mcp/` 的闭合 catalog。

不得记录实现不接受的 `help`、`update`、`uninstall`、alias 或其他推测命令。内部 Host 命令、用户
shell 命令、对话 selector 和 MCP tool 必须明确分层，不能写成同一种调用方式。

## 翻译不变量

所有 locale 必须保持以下内容一致：

- 命令、selector、工具名、环境变量、路径和文件名；
- 产品版本、bundled Core、平台与 Host 兼容范围；
- Node、Transition、错误码、Schema、Recovery classification 和技术标识符；
- 表格行对应关系及其中的事实值；
- 代码命令、Mermaid 拓扑、节点 ID 和支持声明；
- 能力、非目标、限制和验证证据的含义。

叙述性文字、章节标题和图表说明可以按目标语言调整。链接应保持相同语义，并可指向对应语言的
本地化文件。没有稳定译法的标识符保留英文，不为不同 locale 发明不同的产品术语或额外承诺。
翻译不能扩大、缩小或重新解释产品行为。

## 审查要求

文档或产品 Pull Request 至少检查：

- 语言导航中的每个文件存在且互相可达；
- 新增、删除或移动的章节在全部根 README 中一致；
- 版本、命令、平台和 Support Matrix 声明没有漂移；
- 所有公开安装代码块使用 `@latest`，所有精确证据表继续使用已验证版本；
- `docs/COMMANDS*` 与当前 CLI parser、DSH lifecycle、Core parser 和 MCP catalog 一致；
- 非英文 README 没有残留占位文本或整段英文 fallback；
- 技术参考的中英文配对文件表达同一事实。
